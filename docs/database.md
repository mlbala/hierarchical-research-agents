# Database

PostgreSQL 14 or newer (developed against 16). All application objects live
in one schema, `research_hive` by default (`DB_SCHEMA`), including Alembic's
`alembic_version` table. The application never creates databases, roles or
extensions, and tables are never created automatically on startup.

## Setup and migrations

```bash
cd backend
uv run python ../scripts/bootstrap_db.py --check   # connectivity, TLS, revision; changes nothing
uv run python ../scripts/bootstrap_db.py           # create schema if permitted, then migrate
# or, if the schema already exists:
uv run alembic upgrade head
```

`bootstrap_db.py` prints the target (host, database, user, schema; never the
password), the TLS mode and whether the connection is encrypted, creates the
schema only if it is missing **and** the credentials are allowed to, and then
runs `alembic upgrade head`. It never drops anything.

Create a new migration after changing `app/db/models.py`:

```bash
cd backend
uv run alembic revision -m "describe the change"   # then write upgrade/downgrade by hand
```

Migrations read the schema name from the Alembic context
(`op.get_context().opts["version_table_schema"]`), so they work with any
`DB_SCHEMA`.

## Tables

All primary keys are UUIDs generated by the application, except `run_events`
(an identity column so events have a strict order for SSE replay). Timestamps
are `TIMESTAMPTZ` stored in UTC.

### `projects`
`id`, `name` (1–120 chars, checked), `description`, `created_at`, `updated_at`.

### `research_runs`
One research request and its execution record.

| Column | Notes |
| --- | --- |
| `project_id` | FK → projects (cascade) |
| `question`, `context`, `input_urls` (JSONB list) | the request |
| `depth` | `quick` \| `standard` (check constraint) |
| `status` | `queued`, `running`, `completed`, `partial`, `failed`, `cancelled`, `interrupted` (check) |
| `execution_mode` | `live` \| `demo` (check) |
| `settings_snapshot` (JSONB) | non-secret settings and limits used for the run |
| `plan` (JSONB) | the director's validated plan |
| `warnings` (JSONB list) | user-visible warnings (`code`, `message`) |
| `cancel_requested_at`, `started_at`, `finished_at`, `heartbeat_at` | lifecycle |
| `input_tokens`, `output_tokens`, `llm_call_count`, `tool_call_count` | usage |
| `estimated_cost_usd` | NULL = unknown (no pricing configured) |
| `error_code`, `error_message` | sanitised |
| `idempotency_key` | **unique**; prevents double-submitted runs |

Indexes: `(status, created_at)`, `(project_id, created_at)`.

### `agent_tasks`
One row per agent task attempt: `agent_role` (check: the seven roles),
`task_key` (e.g. `data_researcher.research`), `attempt`, `status`
(`running`, `completed`, `failed`, `skipped`, `cancelled`, `interrupted`),
`input_summary`, `output` (JSONB summary, never chain-of-thought), timing,
tokens, sanitised error.

* `UNIQUE (run_id, task_key, attempt)` — unique task attempts.
* `UNIQUE (id, run_id)` — target for composite foreign keys.
* `FOREIGN KEY (parent_task_id, run_id) → agent_tasks (id, run_id)` — a parent
  task must belong to the same run.
* Index on `run_id`.

### `sources`
`url`, `normalized_url_hash` (SHA-256 of the normalised URL), `title`,
`publisher`, `published_at`, `retrieved_at`, `content_hash` (SHA-256 of the
stored text), `content_text` (bounded extracted text), `content_kind`
(`fetched_page` \| `search_snippet` \| `demo`), `metadata` (JSONB: redirects,
truncation, byte count…).

* `UNIQUE (run_id, normalized_url_hash)` — de-duplication within a run.
* `UNIQUE (id, run_id)`; index on `run_id`; GIN full-text index.

### `findings`
`claim`, `evidence_excerpt` (verified verbatim), `support_level`
(`supported` \| `tentative` \| `conflicting`).

* `FOREIGN KEY (source_id, run_id) → sources (id, run_id)` and
  `FOREIGN KEY (task_id, run_id) → agent_tasks (id, run_id)`: a finding can
  only cite a source, and come from a task, **of the same run**.
* Indexes on `run_id` and `source_id`.

### `reports`
`run_id` (**unique**), `title`, `executive_summary`, `body_markdown`
(everything after the summary, including the sources list), `limitations`
(JSONB list), `is_partial`. GIN full-text index over title + summary + body.

### `report_citations`
`report_id`, `source_id`, `citation_number` (≥ 1),
`UNIQUE (report_id, citation_number)`, `UNIQUE (report_id, source_id)`.
This table has no `run_id`, so run ownership of cited sources is enforced in
the service layer (`EvidenceStore.assert_sources_in_run`) in the same
transaction that writes the report; the tests cover the rejection.

### `run_events`
`id` (BIGINT identity), `run_id`, `task_id` (nullable,
`FOREIGN KEY (task_id, run_id) → agent_tasks (id, run_id)`), `event_type`,
`level` (`debug` \| `info` \| `warning` \| `error`), `message`, `payload`
(JSONB, sanitised), `created_at`. Index `(run_id, id)` for ordered replay.

## Full-text search

Expression GIN indexes:

```sql
to_tsvector('english'::regconfig, coalesce(title,'') || ' ' || coalesce(content_text,''))          -- sources
to_tsvector('english'::regconfig, coalesce(title,'') || ' ' || coalesce(executive_summary,'')
                                  || ' ' || coalesce(body_markdown,''))                                -- reports
```

Queries use `websearch_to_tsquery('english', :q)` (bound parameter, so quotes,
`OR` and `-term` work safely). Report search powers `/api/v1/search/reports`;
source ranking is used, scoped to the current run, when a run has more
approved findings than the writers' prompt budget allows.

## Vector search (future option)

Version one deliberately has **no embeddings and no vector tables**. If
semantic search becomes useful, `pgvector` can be added to the same
PostgreSQL database (Aiven supports it), but it requires:

1. an administrator to run `CREATE EXTENSION vector` (the app never creates
   extensions);
2. choosing an embedding model and provider (an extra paid API, or a local
   model) and fixing its embedding dimension;
3. a migration adding a `vector(<dimension>)` column or table plus an index
   (HNSW or IVFFlat), and a backfill job for existing sources;
4. re-embedding everything if the model or dimension ever changes.

## Least-privilege roles (recommended)

Use a separate migration role that owns the schema and a runtime role that
can only read and write rows.

**Step 1 — as an administrator** (on Aiven, `avnadmin`), replacing passwords:

```sql
-- Optional: a dedicated database (or keep using an existing one).
CREATE DATABASE research_hive;
\c research_hive

CREATE ROLE research_hive_migrator LOGIN PASSWORD 'change-me-migrator';
CREATE ROLE research_hive_app      LOGIN PASSWORD 'change-me-app';
-- Lets the migrator create (and therefore own) its schema.
GRANT CREATE ON DATABASE research_hive TO research_hive_migrator;
```

**Step 2 — connected as `research_hive_migrator`**. The migrator creates the
schema itself and sets default privileges for the tables it will create.
(Doing this as the migrator avoids `CREATE SCHEMA … AUTHORIZATION`, which on
PostgreSQL 16+ requires the administrator to be able to `SET ROLE` to the
migrator.)

```sql
CREATE SCHEMA research_hive;
GRANT USAGE ON SCHEMA research_hive TO research_hive_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA research_hive
  GRANT SELECT, INSERT, UPDATE ON TABLES TO research_hive_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA research_hive
  GRANT USAGE, SELECT ON SEQUENCES TO research_hive_app;
```

Then run migrations with the migrator credentials and the app with the
runtime credentials:

```bash
cd backend
PGUSER=research_hive_migrator PGPASSWORD='…' uv run python ../scripts/bootstrap_db.py
# .env for the running app:
#   PGUSER=research_hive_app
#   PGPASSWORD=…
```

If tables already exist (migrated before the default privileges were set),
grant them once as the migrator:

```sql
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA research_hive TO research_hive_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA research_hive TO research_hive_app;
```

The runtime role needs no `DELETE`, `TRUNCATE`, `CREATE` or superuser rights.
Session advisory locks (used for the single-worker guarantee) need no grants.
This exact procedure was verified on PostgreSQL 16 with a non-superuser
administrator: migrations ran as the migrator, a full demo research run
completed as the runtime role, and `DELETE`/`CREATE` were refused for it.

## Connection pool

`DB_POOL_SIZE=3` and `DB_MAX_OVERFLOW=2` (≤ 5 connections) plus one dedicated
connection for the worker's advisory lock. Connections use `pool_pre_ping`
and are recycled every 30 minutes. Connect to the PostgreSQL service port
directly, **not** through a transaction-mode connection pooler (PgBouncer):
session advisory locks and the `statement_timeout` startup option need a real
session. If you must use a pooler, set `DB_STATEMENT_TIMEOUT_MS=0` and run a
single instance only.
